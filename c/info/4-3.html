4.3.1버전 관리와 코드 검토

여러 사람이 같은 코드를 고치려면 누가 언제 무엇을 바꾸었는지 기록하고, 서로의 변경을 합칠 수 있어야 한다. 깃(Git) 같은 버전 관리 도구는 코드의 변경을 커밋이라는 단위로 저장하고, 각자 가지(브랜치)를 만들어 따로 작업한 뒤 합치게 해 준다. 오픈소스 프로젝트에서는 누군가 변경을 제안하면(풀 리퀘스트), 다른 개발자들이 그 코드를 읽고 문제를 지적하며 토론한다. 이것이 코드 검토이다. 검토를 통과하고 자동 시험을 모두 통과한 변경만 본래 코드에 합쳐진다.

정리 4.3.1 여러 검토자의 효과

검토자 한 명이 어떤 버그를 찾을 확률이 \(p\)이고, \(k\)명이 서로 독립적으로 검토하면, 누군가 그 버그를 찾을 확률은 \[1 - (1 - p)^k\]이다. 한 명의 \(p\)가 작아도 \(k\)가 늘면 빠르게 1에 가까워진다. 다만 모두 같은 곳을 놓치는 식으로 검토가 독립적이지 않으면 효과가 줄어든다.

그림 1에서 두 값을 바꾸어 보자. 한 명이 30% 확률로 찾는 버그를 3명이 보면 약 66%, 5명이 보면 약 83%, 10명이 보면 97%의 확률로 누군가 찾아낸다. 수천 명이 쓰고 읽는 오픈소스는 이 효과가 아주 크다. 그래서 '보는 눈이 충분히 많으면 모든 버그는 얕다'는 말이 생겼다. 다만 검토자들이 같은 배경과 습관을 가지면 같은 곳을 함께 놓치므로, 서로 다른 사람들이 검토하는 것이 중요하다.1

4.3.2라이선스와 협업 규칙

오픈소스라고 해서 아무렇게나 써도 되는 것은 아니다. 코드의 저작자는 라이선스로 다른 사람이 그 코드를 어떤 조건으로 쓰고, 고치고, 다시 배포할 수 있는지 밝힌다. MIT 라이선스처럼 저작권 표시만 남기면 거의 자유롭게 쓰게 하는 것이 있고, GPL처럼 그 코드를 고쳐 배포할 때 고친 코드도 같은 조건으로 공개하게 하는 것이 있다. 프로젝트에는 코드 스타일, 커밋 메시지 쓰는 법, 버그를 알리는 방법, 서로를 존중하는 행동 강령 같은 협업 규칙도 있다. 이런 도구와 규칙 덕분에 서로 모르는 사람들도 함께 일할 수 있다.

4.3.3예제 하나를 끝까지

예제 4.3.2

어떤 버그를 검토자 한 명이 찾을 확률이 20%이다. 이 버그를 90% 넘는 확률로 찾으려면 서로 독립적인 검토자가 몇 명 필요한가? 검토자들이 모두 같은 습관을 가져 한 명이 놓치면 다른 사람도 절반의 확률로 함께 놓친다면 어떻게 될지 설명하여라.

\(1 - 0.8^k > 0.9\)이어야 하므로 \(0.8^k < 0.1\)이다. \(0.8^{10} \approx 0.107\), \(0.8^{11} \approx 0.086\)이므로 11명이 필요하다.

검토자들이 독립적이지 않으면, 한 명이 놓친 버그를 다른 사람들도 놓칠 가능성이 커진다. 그러면 \(0.8^k\)보다 놓칠 확률이 훨씬 커서, 11명이 보아도 90%에 이르지 못한다. 극단적으로 모두가 똑같이 생각한다면 몇 명이 보든 한 명이 본 것과 같다. 즉 검토의 힘은 사람의 수만큼 서로 다른 관점에서 나온다. 그래서 큰 오픈소스 프로젝트는 다양한 배경의 기여자를 모으고, 자동 시험처럼 사람과 다른 방식의 검사도 함께 쓴다.

  2. 복원git은 파일의 변경 이력을 커밋 단위로 저장하는 버전 관리 도구이다. 브랜치는 커밋 이력의 갈래로, 각자 자기 브랜치에서 작업하면 남의 작업과 섞이지 않는다. GitHub, GitLab 같은 서비스는 git 저장소를 인터넷에 두고 함께 쓰게 해 준다.

  3. 설명병합(merge)할 때 git은 두 브랜치의 마지막 커밋과 둘이 갈라진 공통 조상, 세 가지를 비교한다(3-way merge). 한쪽만 고친 부분은 고친 쪽을 자동으로 택하고, 양쪽이 같은 곳을 서로 다르게 고쳤으면 어느 것을 택할지 판단하지 못해 충돌(conflict)을 알린다. 충돌한 곳에는 <<<<<<<, =======, >>>>>>> 표시가 들어가며, 사람이 내용을 보고 고친 뒤 커밋해야 병합이 끝난다.

  4. 연결오픈소스 협업에서는 보통 저장소를 복제(fork)하거나 브랜치를 만들어 고친 뒤 풀 리퀘스트(pull request)로 병합을 요청한다. 다른 사람이 코드를 검토(code review)하고 자동 테스트가 통과하면 병합한다. 작은 단위로 자주 커밋하고 자주 병합할수록 충돌이 작고 풀기 쉽다.

# 터미널에서:  pip install pandas
      import pandas as pd
      from collections import Counter

      df = pd.read_csv("lunch.csv")              # 날짜, 메뉴, 잔반kg 열이 있는 표
      top = df.groupby("메뉴")["잔반kg"].mean().sort_values(ascending=False).head(10)
      print(top)
      print(Counter(df["메뉴"]).most_common(3))  # 가장 자주 나온 메뉴 3개

3라이선스, 쓰는 조건을 읽는 법

          
저작권법에 따라 코드도 만든 사람의 저작물이다. 라이선스가 없는 코드는 웹에 공개되어 있어도 원칙적으로 저작권자의 허락 없이 복제하거나 고쳐 배포할 수 없다. 라이선스는 저작권자가 미리 허락해 둔 조건이다. 코드에 쓰는 라이선스는 크게 허용형과 카피레프트 두 갈래이고, 그림·글·자료에는 주로 크리에이티브 커먼즈(CC) 라이선스를 쓴다.

프로젝트에 다른 사람의 코드나 라이브러리를 썼다면 README에 출처와 라이선스를 적는다. 산출물을 공개할 때는 내 코드에 어떤 라이선스를 붙일지도 정한다. 사용한 라이브러리가 GPL이면 내 프로그램을 배포할 때 GPL 조건을 따라야 하므로, 라이브러리를 고르는 단계에서 라이선스를 확인한다.

          
판단“GitHub에 공개되어 있으니 자유롭게 써도 된다”, “오픈소스는 상업적으로 쓸 수 없다”는 둘 다 흔한 오해이다. 공개와 이용 허락은 별개이며, 대부분의 오픈소스 라이선스는 조건만 지키면 상업적 이용도 허락한다. 또 GPL의 소스 공개 의무는 프로그램을 다른 사람에게 배포할 때 생기며, 혼자 쓰거나 모둠 안에서 시험하는 것만으로 생기지는 않는다. 정확한 조건은 반드시 라이선스 원문을 확인한다.
