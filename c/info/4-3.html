4.3.1

두 사람이 같은 파일을 고치면 git은 어떻게 합칠까?

오픈소스 협업 · 브랜치, 병합, 충돌

main 브랜치 (민지가 고침)

fix-empty 브랜치 (준호가 고침)

브랜치마다 고칠 줄을 고른 뒤 병합하세요.


              
stats.py의 처음 내용(공통 조상)에서 두 브랜치가 갈라졌습니다. 파란 띠는 main의 변경, 노란 띠는 fix-empty의 변경입니다. 실제 git처럼 같은 줄이나 바로 붙은 줄을 양쪽이 서로 다르게 고치면 충돌로 처리합니다.

            

          

          
    
            
  1. 질문오픈소스 프로젝트에는 서로 만난 적 없는 수백 명이 코드를 고칩니다. 두 사람이 같은 파일을 동시에 고치면, 한 사람의 수정이 다른 사람의 수정을 덮어써 버리지 않을까요?
    2. 
            
  2. 복원git은 파일의 변경 이력을 커밋 단위로 저장하는 버전 관리 도구입니다. 브랜치는 커밋 이력의 갈래로, 각자 자기 브랜치에서 작업하면 남의 작업과 섞이지 않습니다. GitHub, GitLab 같은 서비스는 git 저장소를 인터넷에 두고 함께 쓰게 해 줍니다.
    3. 
            
  3. 설명병합(merge)할 때 git은 두 브랜치의 마지막 커밋과 둘이 갈라진 공통 조상, 세 가지를 비교합니다(3-way merge). 한쪽만 고친 부분은 고친 쪽을 자동으로 택하고, 양쪽이 같은 곳을 서로 다르게 고쳤으면 어느 것을 택할지 판단하지 못해 충돌(conflict)을 알립니다. 충돌한 곳에는 <<<<<<<, =======, >>>>>>> 표시가 들어가며, 사람이 내용을 보고 고친 뒤 커밋해야 병합이 끝납니다.
    4. 
            
  4. 연결오픈소스 협업에서는 보통 저장소를 복제(fork)하거나 브랜치를 만들어 고친 뒤 풀 리퀘스트(pull request)로 병합을 요청합니다. 다른 사람이 코드를 검토(code review)하고 자동 테스트가 통과하면 병합합니다. 작은 단위로 자주 커밋하고 자주 병합할수록 충돌이 작고 풀기 쉽습니다.
    5. 
            
  5. 적용main에서 5줄(반올림), fix-empty에서 7줄(빈 리스트로 시험)만 고르고 병합해 보세요. 그다음 양쪽 모두 5줄을 고르고 병합하면 무엇이 달라지나요? 충돌을 세 가지 방법으로 풀어 결과를 비교하고, main의 1줄과 fix-empty의 2줄처럼 붙어 있는 두 줄을 각각 고치면 어떻게 되는지도 확인하세요.
    6. 
            
  6. 판단충돌이 없다고 병합 결과가 옳다는 보장은 없습니다. 두 사람이 서로 다른 줄을 고쳤어도, 합쳐진 코드가 함께 동작하지 않을 수 있습니다. 예를 들어 5줄 충돌을 ‘main 쪽 선택’으로 풀면, 충돌 없이 들어온 fix-empty의 7줄 print(average([]))는 실행하자마자 ZeroDivisionError를 냅니다. 그래서 병합한 뒤에는 반드시 테스트를 다시 돌립니다. ‘한쪽 선택’으로 충돌을 지우면 다른 사람의 수정이 조용히 사라질 수 있으니, 두 변경의 의도를 확인하고 합쳐야 합니다.
    7.

          4.3.2
인터넷에 공개된 코드는 마음대로 가져다 써도 될까?
읽기 · 라이브러리 활용, 협업 흐름, 오픈소스 라이선스
        

        

          
CSV 파일 읽기, 그래프 그리기, 정렬처럼 많은 사람이 필요로 하는 기능은 이미 누군가 만들어 공개해 두었습니다. 이것을 쓰면 프로젝트의 핵심 문제에 시간을 쓸 수 있습니다. 그런데 공개되어 있다는 것과 마음대로 써도 된다는 것은 같은 뜻일까요?

          
1라이브러리를 활용해 협력하기

          
오픈소스는 소스 코드를 공개하고, 정해진 조건(라이선스) 아래에서 누구나 쓰고 고치고 다시 배포할 수 있게 한 소프트웨어입니다. 파이썬에는 설치하지 않아도 쓰는 표준 라이브러리(csv, collections, random 등)가 있고, 그 밖의 라이브러리는 PyPI 저장소에서 pip로 설치합니다.

          
# 터미널에서:  pip install pandas
      import pandas as pd
      from collections import Counter

      df = pd.read_csv("lunch.csv")              # 날짜, 메뉴, 잔반kg 열이 있는 표
      top = df.groupby("메뉴")["잔반kg"].mean().sort_values(ascending=False).head(10)
      print(top)
      print(Counter(df["메뉴"]).most_common(3))  # 가장 자주 나온 메뉴 3개

          
라이브러리를 쓸 때는 공식 문서와 예제를 먼저 읽고, 프로젝트에서 쓴 라이브러리와 버전을 requirements.txt 같은 파일에 적어 둡니다. 그래야 다른 모둠원의 컴퓨터에서도 같은 결과가 나옵니다.

          
2오픈소스 프로젝트가 함께 일하는 방식

          
    
            
  • 이슈(issue): 버그 신고나 새 기능 제안을 글로 남기고 토론합니다.
    • 
            
  • 포크·브랜치: 원래 저장소를 복제하거나 브랜치를 만들어 그 안에서 고칩니다.
    • 
            
  • 풀 리퀘스트: 고친 내용을 원래 저장소에 합쳐 달라고 요청합니다. 무엇을 왜 고쳤는지 설명을 붙입니다.
    • 
            
  • 코드 리뷰와 자동 테스트: 관리자와 다른 기여자가 코드를 읽고 의견을 남기며, 테스트가 통과해야 병합됩니다.
    • 
            
  • 문서: README(무엇을 하는 프로그램이며 어떻게 쓰는가), CONTRIBUTING(기여하는 방법), LICENSE(이용 조건) 파일을 둡니다.
    • 
          

          
3라이선스: 쓰는 조건을 읽는 법

          
저작권법에 따라 코드도 만든 사람의 저작물입니다. 라이선스가 없는 코드는 웹에 공개되어 있어도 원칙적으로 저작권자의 허락 없이 복제하거나 고쳐 배포할 수 없습니다. 라이선스는 저작권자가 미리 허락해 둔 조건입니다. 코드에 쓰는 라이선스는 크게 허용형과 카피레프트 두 갈래이고, 그림·글·자료에는 주로 크리에이티브 커먼즈(CC) 라이선스를 씁니다.

          

            
라이선스갈래지켜야 할 주요 조건쓰는 예

            
              
MIT허용형저작권 표시와 라이선스 전문을 함께 배포. 수정·상업적 이용 가능. 보증 없음많은 소규모 라이브러리

              
BSD 3-Clause허용형MIT와 비슷하고, 원저작자의 이름을 허락 없이 홍보에 쓰지 않을 것NumPy, pandas, scikit-learn

              
Apache 2.0허용형라이선스와 NOTICE 파일 포함, 수정한 파일에 변경 사실 표시. 특허 사용 허락 조항 포함requests

              
GPL 3.0카피레프트이 코드를 포함한 프로그램을 배포하면 전체 소스 코드를 같은 GPL로 공개GNU 도구들

              
CC BY, CC BY-SA콘텐츠용저작자 표시(BY), 같은 조건으로 공유(SA). 코드보다는 그림·글·자료에 씀위키백과 글(CC BY-SA)

            
          

          
프로젝트에 다른 사람의 코드나 라이브러리를 썼다면 README에 출처와 라이선스를 적습니다. 산출물을 공개할 때는 내 코드에 어떤 라이선스를 붙일지도 정합니다. 사용한 라이브러리가 GPL이면 내 프로그램을 배포할 때 GPL 조건을 따라야 하므로, 라이브러리를 고르는 단계에서 라이선스를 확인합니다.

          
판단“GitHub에 공개되어 있으니 자유롭게 써도 된다”, “오픈소스는 상업적으로 쓸 수 없다”는 둘 다 흔한 오해입니다. 공개와 이용 허락은 별개이며, 대부분의 오픈소스 라이선스는 조건만 지키면 상업적 이용도 허락합니다. 또 GPL의 소스 공개 의무는 프로그램을 다른 사람에게 배포할 때 생기며, 혼자 쓰거나 모둠 안에서 시험하는 것만으로 생기지는 않습니다. 정확한 조건은 반드시 라이선스 원문을 확인합니다.
