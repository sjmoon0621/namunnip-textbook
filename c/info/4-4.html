기대값은 명세(함수가 해야 할 일)대로 계산한 값입니다. 실패한 줄의 ‘추적’을 누르면 그 입력으로 함수를 한 줄씩 실행하며 변수 값을 볼 수 있습니다.

          

          
    
            
  1. 질문윤년 판별 함수를 2024년과 2023년으로 시험했더니 둘 다 맞았습니다. 이 함수는 이제 믿어도 될까요? 어떤 입력을 더 넣어 봐야 할까요?
    2. 
            
  2. 복원프로그램은 명세(입력에 대해 무엇을 돌려줘야 하는가)를 만족해야 합니다. 그레고리력에서 윤년은 4로 나누어떨어지는 해 가운데, 100으로 나누어떨어지는 해는 빼고, 400으로 나누어떨어지는 해는 다시 넣습니다.
    3. 
            
  3. 설명단위 테스트는 함수 하나에 입력을 넣고 결과가 기대값과 같은지 자동으로 확인하는 코드입니다. 파이썬에서는 assert is_leap(2000) == True처럼 쓰거나 unittest, pytest를 씁니다. 좋은 테스트는 평범한 값뿐 아니라 규칙이 바뀌는 경계값(1900, 2000, 리스트의 맨 끝 원소)과 예외 경우(빈 리스트, 원소가 하나인 리스트)를 고루 넣습니다. 테스트가 실패하면 디버깅을 합니다. 실패한 입력으로 코드를 한 줄씩 따라가며(추적) 변수 값이 예상과 처음 달라지는 곳을 찾습니다.
    4. 
            
  4. 연결버그를 고친 뒤에는 처음에 통과하던 테스트까지 모두 다시 돌립니다(회귀 테스트). 고친 부분이 다른 곳을 망가뜨리지 않았는지 확인하기 위해서입니다. 협업 저장소에서는 커밋할 때마다 테스트가 자동으로 돌도록 설정해 두기도 합니다.
    5. 
            
  5. 적용세 함수마다 평범한 테스트만으로 시작해 모두 통과하는지 보고, 경계값과 예외 경우를 하나씩 더해 실패하는 테스트를 찾으세요. 실패한 테스트를 추적해 버그가 있는 줄을 짚은 다음 ‘고친 코드 적용’을 누르고 모든 테스트를 다시 실행하세요.
    6. 
            
  6. 판단테스트를 모두 통과해도 버그가 없다는 증명은 아닙니다. 테스트는 버그가 있음을 보여 줄 수는 있지만 없음을 보여 주지는 못합니다. 그래서 테스트의 개수보다 입력을 성질이 같은 묶음으로 나누어(동등 분할) 묶음마다, 그리고 그 경계마다 골고루 넣는 것이 중요합니다.
    7.

          4.4.2
버그는 어떤 순서로 잡아야 할까?
읽기 · unittest로 테스트 자동화, 디버깅 과정
        

        

          
프로그램이 틀린 답을 냅니다. 코드를 처음부터 눈으로 다시 읽으면 찾을 수 있을까요? 코드가 수백 줄이 넘으면 그렇게 해서는 끝이 나지 않습니다.

          
1테스트를 코드로 남기기

          
테스트를 손으로 매번 입력하면 귀찮아서 결국 덜 하게 됩니다. 파이썬 표준 라이브러리의 unittest로 테스트를 파일에 적어 두면, 명령 한 줄로 언제든 모두 다시 돌릴 수 있습니다.

          
import unittest
      from stats import median

      class TestMedian(unittest.TestCase):
          def test_odd(self):
              self.assertEqual(median([3, 1, 2]), 2)

          def test_even(self):                        # 경계: 짝수 개
              self.assertEqual(median([4, 1, 3, 2]), 2.5)

          def test_empty(self):                       # 예외 경우
              with self.assertRaises(ValueError):
                  median([])

      if __name__ == "__main__":
          unittest.main()

          
실행하면 통과한 테스트는 점(.)으로, 실패한 테스트는 F, 예상하지 못한 오류는 E로 표시되고, 실패한 테스트마다 기대값과 실제 값을 보여 줍니다. 버그를 고칠 때마다 이 파일을 다시 돌리면 회귀 테스트가 됩니다. 실무에서는 pytest처럼 더 간결하게 쓰는 외부 라이브러리도 많이 씁니다.

          
2디버깅의 순서

          
    
            
  • 재현: 버그가 언제나 나타나는 가장 작은 입력을 찾습니다. 그 입력을 그대로 테스트로 만들어 둡니다.
    • 
            
  • 범위 좁히기: 중간 값을 print로 찍거나, 개발 환경의 디버거로 중단점(breakpoint)을 걸고 한 줄씩 실행하며 변수를 봅니다. 값이 처음으로 예상과 달라지는 줄 근처에 원인이 있습니다. 코드의 절반씩을 확인해 나가면 이진 탐색처럼 빠르게 좁혀집니다.
    • 
            
  • 원인 이해: 증상(틀린 출력)이 아니라 원인(잘못된 조건, 경계 처리, 자료형)을 찾습니다. 왜 틀렸는지 설명할 수 있어야 제대로 고친 것입니다.
    • 
            
  • 수정과 확인: 고친 뒤 재현 테스트가 통과하는지, 기존 테스트도 모두 통과하는지 확인합니다.
    • 
            
  • 기록: 커밋 메시지나 이슈에 무엇이 원인이었고 어떻게 고쳤는지 남깁니다.
    •
