4.2.1

코딩부터 시작하면 왜 프로젝트가 꼬일까?

읽기 · 문제 분석에서 검증까지의 설계

주제를 정하자마자 코드부터 쓰기 시작하면, 며칠 뒤 “이 자료는 어떻게 저장하지?”, “이 함수는 누가 만들었지?” 같은 문제가 한꺼번에 터집니다. 프로젝트 수행 과정을 미리 설계하면 무엇을 피할 수 있을까요?

1프로그래밍으로 문제를 해결하는 네 단계

단계할 일잔반 분석 프로젝트의 예
문제 분석과 구조화입력·출력·제약을 정하고, 자료를 어떤 구조(리스트, 사전, 그래프)로 나타낼지 정한다날짜를 키로, (메뉴 목록, 잔반 kg)을 값으로 하는 사전
알고리즘 설계해결 방법을 의사코드나 순서도로 쓰고, 여러 후보의 효율(빅오)을 비교한다메뉴별 평균 잔반 계산 O(n), 정렬해 상위 10개 O(n log n)
프로그래밍(자동화)언어와 라이브러리를 고르고, 기능을 함수·모듈로 나누어 구현한다파이썬, CSV 읽기는 csv 모듈, 그래프는 matplotlib
검증테스트로 정확성을 확인하고, 다른 자료와 환경에서도 잘 동작하는지 평가한다손으로 계산한 3일치 결과와 비교, 2학기 자료로 다시 실행

네 단계는 한 번에 끝나는 직선이 아닙니다. 검증에서 문제가 나오면 설계로, 때로는 문제 정의로 돌아갑니다. 그래서 작은 기능 하나를 네 단계 모두 거쳐 완성한 다음 기능을 늘려 가는 방식이 실패를 줄입니다.

3모둠이 함께 정할 것

  • 주제와 언어: 후보를 모두 적고 장단점을 비교한 뒤 투표 등 모둠이 합의한 방법으로 정합니다. 목소리 큰 한 사람이 정하지 않습니다.
  • 역할: 자료 담당, 알고리즘 담당, 화면 담당, 테스트 담당처럼 나누되, 모두가 코드 일부를 쓰고 서로의 코드를 읽어 봅니다.
  • 일정: 작업을 나누고 선행 관계를 그려 임계 경로를 찾고, 중간 점검일을 둡니다.
  • 도구: 코드는 git 저장소에 두고, 할 일과 문제는 이슈 목록이나 공유 문서에 적습니다.
  • 완성의 기준: 어떤 테스트를 통과하면 끝난 것으로 볼지 처음에 정해 둡니다.

판단계획은 처음부터 완벽할 수 없으며, 계획대로 되지 않는 것이 실패도 아닙니다. 중요한 것은 바뀐 내용을 기록하고 모둠이 함께 아는 것입니다. 반대로 계획을 세우는 데만 시간을 쓰고 아무것도 실행해 보지 않으면 문제를 늦게 발견하게 되므로, 작게 만들어 보고 고치는 과정을 일정에 넣습니다.

4.2.2

프로젝트는 어느 단계가 늦어지면 전체가 늦어질까?

프로젝트 전체 기간

def schedule(dur, pre, order):
          # order: 선행 작업이 언제나 먼저 오도록 정렬한 작업 목록
          start = {}
          for t in order:
              start[t] = max((start[p] + dur[p] for p in pre[t]),
                             default=0)
          return max(start[t] + dur[t] for t in order)

고등학생 모둠의 정보과학 프로젝트(학교 급식 잔반 기록을 분석하는 프로그램)를 가정한 모식 일정입니다. 막대 사이의 회색 선은 “앞 작업이 끝나야 시작할 수 있다”는 선행 관계입니다.

  1. 질문모둠 프로젝트의 마감이 3주 뒤입니다. 할 일을 나누고 각자 맡았는데, 어떤 일은 하루 늦어져도 괜찮고 어떤 일은 하루 늦어지면 발표도 하루 늦어집니다. 어느 작업을 가장 신경 써야 할까요?
  2. 복원프로그래밍으로 문제를 해결하는 절차는 문제 분석과 구조화 → 알고리즘 설계 → 프로그래밍(자동화) → 검증입니다. 작업 사이의 “먼저 끝나야 하는” 관계는 방향 그래프로 나타낼 수 있습니다.
  3. 설명프로젝트를 크기가 작은 작업으로 나누는 것을 작업 분해라 합니다. 각 작업은 모든 선행 작업이 끝난 뒤에야 시작할 수 있으므로, 가장 이른 시작일은 선행 작업의 (시작일 + 기간) 중 가장 큰 값입니다. 선행 관계를 지키는 순서(위상 정렬)로 작업을 하나씩 계산하면 전체 기간이 나옵니다. 처음부터 끝까지 이어지는 가장 긴 작업 사슬이 임계 경로이며, 이 경로의 작업은 하루만 늦어져도 전체가 늦어집니다.
  4. 연결임계 경로 밖의 작업에는 여유가 있어, 그만큼 늦어져도 마감에 영향이 없습니다. 모둠원은 여유가 있는 작업을 맡은 사람이 임계 경로의 작업을 돕는 식으로 역할을 조정할 수 있습니다. 코드에서 각 작업을 한 번씩만 계산하는 것은 앞에서 배운 동적 계획법과 같은 생각입니다.
  5. 적용‘자료 수집’의 기간을 4일에서 8일로 늘려 보세요. 전체 기간이 바로 늘어나나요? 임계 경로가 바뀌는 순간은 언제인가요? 반대로 ‘프로그래밍’을 하루 줄이면 전체 기간은 몇 일 줄어드나요?
  6. 판단이 계산은 작업 기간을 정확히 안다고 가정하고, 한 사람이 여러 작업을 동시에 할 수 없다는 제약도 넣지 않았습니다. 실제 프로젝트에서는 예상이 자주 빗나가므로 임계 경로에 여유 기간을 두고, 중간 점검일을 정해 계획을 고칩니다. 주제와 사용할 언어처럼 모둠 전체에 영향을 주는 결정은 한 사람이 정하지 말고 함께 협의해 정합니다.
