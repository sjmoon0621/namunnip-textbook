피보나치 수열은 앞의 두 수를 더해 다음 수를 만든다. 정의가 'fib(n) = fib(n − 1) + fib(n − 2)'이니 재귀 함수로 옮기면 두 줄이면 된다. 그런데 이 함수로 fib(40)을 구하면 컴퓨터가 몇 초 동안 멈춰 있고, fib(50)은 몇 분을 기다려야 한다. 반복문으로 앞에서부터 차례로 더하면 fib(50)도 눈 깜짝할 사이에 나온다. 같은 정의를 옮긴 두 프로그램이 왜 이렇게 다를까?

먼저 알아야 할 것재귀 구조(재귀 구조), 반복문, 수열과 점화식(수학).

1.3.1같은 계산의 되풀이

재귀로 fib(5)를 구하면 fib(4)와 fib(3)을 부른다. 그런데 fib(4)도 fib(3)과 fib(2)를 부른다. 그래서 fib(3)은 두 번, fib(2)는 세 번, fib(1)은 다섯 번 계산된다. n이 커질수록 같은 값을 계산하는 횟수가 폭발적으로 늘어난다. 호출들을 나무로 그리면 가지가 둘씩 갈라지는 커다란 나무가 되고, 그 나무의 마디 수가 곧 호출 수이다. 반복문은 fib(0)과 fib(1)에서 시작해 두 수를 기억하며 앞으로 나아가므로, 각 값을 한 번씩만 계산한다.

정리 1.3.1 재귀 호출의 수

정의 그대로의 재귀로 fib(n)을 구할 때의 호출 수 \(C(n)\)은 \(C(0) = C(1) = 1\), \(C(n) = C(n-1) + C(n-2) + 1\)이고, 이를 풀면 \(C(n) = 2\,\text{fib}(n+1) - 1\)이다. fib(n)은 n이 1 늘 때마다 약 1.618배가 되므로 호출 수도 지수적으로 늘어난다. 반복문은 \(n\)번이면 된다.

그림 1에서 n을 바꾸어 보자. fib(30)은 재귀로 약 270만 번, fib(40)은 약 3억 3천만 번을 호출한다. 1초에 1억 번 호출한다고 해도 fib(40)은 약 3.3초, fib(50)은 약 400억 번으로 7분 가까이 걸린다. 반복문은 fib(50)을 50번 더하면 끝난다. 재귀와 반복의 차이가 아니라, 같은 계산을 되풀이하느냐 한 번만 하느냐의 차이이다.1

1.3.2알맞은 방식 고르기

재귀가 늘 느린 것은 아니다. 하노이의 탑이나 폴더 탐색처럼 부분 문제가 서로 겹치지 않으면 재귀가 자연스럽고 효율적이다. 피보나치처럼 부분 문제가 겹치면, 한 번 구한 답을 표에 적어 두었다가 다시 쓰는 메모이제이션을 더하면 재귀도 반복문만큼 빨라진다. 반복문은 스택 프레임을 쌓지 않아 메모리를 적게 쓰고, 아주 깊은 계산에서도 스택이 넘치지 않는다. 그래서 문제의 구조를 보고, 부분 문제가 겹치는지와 깊이가 얼마나 되는지를 따져 방식을 고른다.

fib(6)은 fib(5)와 fib(4)를, fib(5)는 fib(4)와 fib(3)을 부른다. fib(k)가 계산되는 횟수를 세면 fib(6) 1번, fib(5) 1번, fib(4) 2번, fib(3) 3번, fib(2) 5번이다. 횟수 자체가 피보나치 수열을 따른다.

1두 방식은 생각하는 방향이 다르다

          
반복구조는 “지금 상태에서 한 걸음 나아가려면 무엇을 바꾸는가”를 묻는다. 변수(합계, 인덱스, 앞의 두 항 등)를 직접 두고, 반복할 때마다 고쳐 나간다. 재귀구조는 “이 문제를 같은 모양의 더 작은 문제로 바꾸면 무엇이 남는가”를 묻는다. 상태는 각 호출의 매개변수와 지역 변수에 나뉘어 담기고, 언어가 호출 스택으로 관리해 준다.

재귀
def deep_sum(x):
          if isinstance(x, int):
              return x
          total = 0
          for y in x:
              total += deep_sum(y)
          return total

            
반복 + 직접 만든 스택
def deep_sum_loop(x):
          total, stack = 0, [x]
          while stack:
              y = stack.pop()
              if isinstance(y, int):
                  total += y
              else:
                  stack.extend(y)
          return total

          

          
두 함수 모두 15를 돌려준다. 재귀 쪽은 “원소가 정수면 그 값, 리스트면 각 원소의 합”이라는 정의를 그대로 옮겼다. 반복 쪽은 앞으로 처리할 것을 담는 스택을 직접 만들었다. 재귀 함수가 호출 스택에 맡기던 일을 손으로 하는 것이다. 이렇게 어떤 재귀든 명시적 스택을 쓰면 반복으로 바꿀 수 있지만, 코드가 길어지고 의도가 덜 드러날 수 있다. 스택은 다음 단원에서 자세히 다룬다.


          
3차례로 훑기만 하는 일은 반복이 낫다

          
1부터 n까지 더하기를 return n + total_rec(n - 1)로 쓰면 깊이가 n이 된다. 파이썬의 재귀 한도는 기본 1000이라(sys.getrecursionlimit()로 확인) total_rec(5000)은 RecursionError를 낸다. 같은 일을 하는 for문은 n이 백만이어도 문제없다. 일부 언어는 마지막 동작이 재귀 호출뿐인 꼬리 재귀를 반복으로 바꿔 주지만, 파이썬은 이 최적화를 하지 않는다.

          
하노이 탑은 반대 예이다. 재귀로는 몇 줄이면 되지만, 반복으로 쓰려면 “가장 작은 원판을 한 방향으로 돌리고, 그 사이에 가능한 다른 이동을 한다” 같은 규칙을 따로 찾아내야 한다. 이동 횟수는 두 방식 모두 2ⁿ − 1로 같고, 깊이는 n이라 한도 걱정도 없다.


          
판단선택의 기준은 취향이 아니라 문제의 구조와 크기이다. 문제가 스스로 닮은 구조이고 깊이가 작으면 재귀가 읽기 쉽고 오류도 적다. 깊이가 입력 크기에 비례해 커지거나, 같은 부분 문제를 되풀이한다면 반복이나 메모이제이션으로 바꾸어야 한다. 어느 쪽이든 옳은지(기저 조건·종료 조건)와 얼마나 걸리는지(호출 수·반복 수)를 따로 따져야 한다.
